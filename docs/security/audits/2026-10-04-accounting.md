## Checked, nothing found

- **A01 Broken access control.**
  - Routes and roles: every `/api/v1` route is behind the `api` firewall; only `auth/(sign-up|sign-in|sign-out|password-reset|invitations)` are public. Signed out, all 61 routes tried answered 401.
  - Matrix, tried live per role: billing and accountant get 403 on all 14 owner-only writes (users, company, logo, resolution, warnings, manual-invoicing confirmation, numbering). Billing gets 403 on all 14 book writes (taxes, payment methods, accounts, posting rules, lock date) and on the 8 VIEW_BOOKS reads and exports; the accountant is allowed all of them. Both roles are allowed all 17 document writes (terceros incl. Ley 1581 export, products, categories, sales/purchase invoices, quotations, receipts, payments).
  - IDOR, tried live as company A's owner with real ids from other companies: 70 requests covering every id route family. Sales invoices, quotations, purchase invoices and attachments, cash receipts, supplier payments, terceros, products, categories, taxes, payment methods, accounts, users and cartera drill-downs: 404 everywhere (PUT `/terceros/{id}` answers 422 validation before loading, and leaks nothing). List filters `?tercero_id=` of another company give an empty page.
  - Ids inside bodies, tried live: tercero, contact, seller, responsible, line product/tax/account, payment method, allocation receivable/payable, product category/taxes/accounts, the company's default taxes, tax and payment-method accounts, posting-rule account and a tercero's account overrides all answer 422/404. A foreign contact id in PUT `/terceros/{id}` creates a new contact; the other company's contact is untouched.
  - Code review: every repository and query (33 files, incl. DBAL) binds `company_id` or reads ids a company-scoped query returned. `AccessToken` and `Company` are the only non-`CompanyOwned` entities, loaded by secret hash or by the session's company. Owner, company and author always come from the session.
  - Files are served only through controllers that check the company.
- **A02 Cryptographic failures.** The `auto` hasher is used. Tokens are `random_bytes(32)`, stored as SHA-256 and found by hash (no comparison of secrets in PHP). They are single use and expire (7 days for an invitation, 1 hour for a reset); a new link revokes the old one, and deactivation revokes all.
  - Tried live: a reused invitation, a reused reset token and an invitation token used as a reset token all answer 404. The token travels after `#` and is stripped from the address bar.
  - `#[\SensitiveParameter]` is on token and password parameters, and no secret is logged (the new security log is asserted not to contain the password). No secrets are in the repository or the bundle (only `NODE_ENV`).
- **A03 Injection.**
  - SQL/DQL: values are bound. The concatenations are constant table/column names, enum-mapped names, `%d` limits, or a bound LIKE value. `LIKE` is escaped (`addcslashes` or `ESCAPE '!'`).
  - XSS: there is no `dangerouslySetInnerHTML`, `innerHTML`, `eval` or user-built `href`. Every Twig template autoescapes, with no `|raw`, and `nl2br` comes after escaping.
  - Tried live: `<script>alert(1)</script><img src=x onerror=…>` in the tercero name, trade name, contact name, product name and description, line descriptions, notes, quotation header/terms and purchase supplier number. The API stores it as text, the PDF prints it literally (checked with `pdftotext`), and the e-mail HTML escapes it (`&lt;script&gt;`).
  - Commands and mail: there is no `exec`/`shell_exec`/`proc_open`/backticks in `src`. E-mail subjects and addresses go through Mime's `Address`/`Email` API.
  - CSV: `CsvEncoder` prefixes `'` on cells starting `=`, `+`, `@`, tab or CR, and on a `-` that is not a number (checked: `=1+1`, `+1`, `-1+2`, `@SUM(A1)`; `-12.5` is kept). Its tests are `CsvEncoderTest`.
- **A04 Insecure design.**
  - Rate limits, tried live:
    - sign-in: 429 after 5 per e-mail+IP, and after 25 per IP
    - password reset: 429 after 5 per IP; one person gets at most 5 e-mails, silently
    - sign-up: 429 after 5 per hour per IP
    - e-mails: now bounded per company (finding 1)
  - Invitation and reset lookups carry a 256-bit token, so they need no limit.
  - State transitions are enforced in the domain (`document_not_draft`, `document_voided`, `quotation_not_open`, `document_has_allocations`, `period_locked`; covered by the functional tests).
  - Mass assignment, tried live: `company_id`, `status`, `number`, `total`, `paid_amount`, `created_by` and `converted_invoice_id` in bodies are ignored, and the documents stay draft with no number. Input DTOs only.
- **A05 Security misconfiguration.**
  - `deploy/env.local.example` sets `APP_ENV=prod` and `APP_DEBUG=0`, and the deploy script refuses anything but prod. The profiler and nelmio are dev/test only.
  - Errors: production answers 500 `internal_error`, and the framework's own messages are never echoed (`ApiExceptionSubscriber`).
  - Cookies, checked on the stack: `PHPSESSID` is `httponly; samesite=lax` with `cookie_secure: auto`.
  - CORS: there is no CORS bundle, so there are no cross-origin grants.
  - Uploads live outside `public/` (`UPLOADS_DIR`, and the deploy script warns if it is inside). nginx and Apache serve only real files in `public/` and send everything else to `index.php`; nginx 404s any other `.php`.
- **A06 Vulnerable components.** `composer audit` and `npm audit --omit=dev` are clean, and the lock files are committed.
- **A07 Identification and authentication.**
  - The session id changes on sign-in. Tried live: a session id planted before sign-in is replaced, and the planted one stays signed out.
  - A changed role, a deactivation or a password reset ends the person's other sessions at their next request. Tried live: 401 on `/me` for the old session in each case; the session that reset the password stays in. A deactivated user cannot sign in and gets no reset e-mail.
  - The 2-hour inactivity expiry is covered by `SessionExpiryTest`.
  - A wrong e-mail and a wrong password give the same 401 `invalid_credentials`, and now take the same time (finding 2). A reset request answers 202 for any address.
  - CSRF: the session cookie is SameSite=Lax, and `SameOriginWrites` refuses writes from another origin. Tried live: `Origin: https://evil.test`, `Origin: null` and `Sec-Fetch-Site: cross-site` or `same-site` all get 403, and a cross-site sign-out gets 403 too. Sign-out by GET gets 405.
- **A08 Software and data integrity.**
  - Uploads: MIME is judged by content, sizes are capped, names are generated, and files are served with `Content-Disposition` and `nosniff`. SVG and HTML are refused (tried live: see leads).
  - Path traversal: storage paths come only from generated UUIDs. Tried: `../`, `%2e%2e` and `%00` in attachment ids (404/400).
  - Messenger: messages are e-mails the app built, serialized by Messenger into its own table, so no client data is deserialized and there is no `unserialize()` in `src`.
- **A09 Logging.** Admin actions are in `audit_log` (users, roles, company, books, Ley 1581). Refused sign-ins and 403s are now logged (finding 5).
- **Frontend.**
  - Open redirects: none. `from` is in-app history state only, and the invitation/reset pages go to `/`.
  - `target="_blank"` links are our own PDFs and carry `rel="noreferrer"`.
  - `localStorage` holds only the theme, validated against an allow-list; there are no tokens.
  - There are no inline scripts or styles, so the strict CSP holds (finding 4).
- **Console commands.** `app:demo:seed` and `app:ledger:demo-entries` refuse `prod`.
- **Deploy.** `cpanel-update.sh`:
  - It refuses a non-prod `.env.local` and warns about a committed `.env`.
  - The database password goes through a 0600 defaults file, never argv.
  - It backs up before migrating, with a truncation check.
  - It keeps uploads outside `public/`, and its cron line uses `flock`.

Notes recorded, not findings:

- **Defence in depth.** `DbalBookSettingsQueries:22`, `DbalJournalQueries:62` and `DbalCarteraQueries:137/143` join `ledger_account`/`journal_entry` by id without repeating `company_id`. They are safe because every write path checks those ids against the company, but an extra `AND a.company_id = …` would remove the dependency.
- **LIKE escaping.** Escaping with `addcslashes` relies on MariaDB's default backslash escape. With `NO_BACKSLASH_ESCAPES`, `%`/`_` would only widen a search inside one's own company.
- **One-use links.** A link is spent without a row lock, so two simultaneous confirmations of the same link could both pass. Only the person holding the link can do that.
- **Queued e-mails.** An e-mail waiting in `messenger_messages` (and in the `failed` queue) contains its invitation/reset link until it is sent.
- **Empty dates.** `""` as `payments[].due_date` on a sales invoice, or as a tax's `valid_from`/`valid_to`, is stored as today instead of none. This is a correctness bug, not a security one, and is passed to the coordinator.

## Not applicable

- **A10 SSRF.** The app makes no server-side request to a URL a user supplies. dompdf has remote loading off, and there are no webhooks and no import-by-URL. The only outbound connection is SMTP to the configured `MAILER_DSN`.
- **JWT / refresh tokens** (A07). Authentication is a server-side session cookie; there are no tokens in the browser.
- **CORS** (A05). The UI is served from the API's own origin, so no cross-origin access is configured.
